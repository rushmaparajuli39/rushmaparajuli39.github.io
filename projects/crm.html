The problem

A group of 20 businesses needs its EIN letters, licenses, and insurance policies in one place, with renewal dates tracked. Different staff should only see the businesses they're responsible for, and it all had to run on free tiers.

  • Monthly cash sheets for each business, with an automatic email listing any that are missing.
  • An audit log of every create, edit, and delete.
  • An admin panel to add staff logins and decide who can see which business.

How access is kept safe

Hiding buttons in the interface isn't security. In this app, the database itself checks every request:

  1. Sign inStaff log in with email and password.
  2. RequestThe app asks for a business's records.
  3. Database checkPostgres Row Level Security looks up the user's role and which businesses they've been granted.
  4. ResultOnly permitted rows come back. Anything else is refused, whatever the app asked for.

The audit log works the same way: nobody can write to it directly. Database triggers add an entry whenever data changes, so nothing is left out.

How I worked

My part was the business side: I wrote the v1 requirements (goal, features, access model, and build order), decided how the tool should work for staff, and tested it against real needs. The code was written and run by Claude, an AI assistant, working from those requirements. Coding isn't my specialty. Since v1, I've added edit and delete, an editor role, the audit log, password reset, and cash sheets as new needs came up. Every change is automatically checked to make sure the app still builds.

Tech stack, for reference: Next.js, TypeScript, Supabase (Postgres), Vercel.

What's next: Sarathi One

Sarathi One is my plan, still at the requirements stage, to turn this into a multi-tenant product any business can sign up for. It would have self-serve sign-up, an isolated workspace for each business, and an installable mobile app (PWA), on the same stack with Row Level Security keeping each business's data separate.
